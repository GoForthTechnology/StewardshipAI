## Context

The project currently uses a Vertex AI RAG corpus that was manually configured through the Google Cloud Console. This makes it difficult to replicate the setup in different environments (e.g., dev, staging, prod) and lacks the benefits of version-controlled infrastructure.

## Goals / Non-Goals

**Goals:**
- Provide a Terraform-based IaC solution for provisioning a Vertex AI RAG corpus.
- Externalize all resource identifiers so the agent can work with any IaC-provisioned RAG environment.
- Ensure the transition from manual to IaC-managed infrastructure is well-documented.

**Non-Goals:**
- Automating the upload of documents to the RAG corpus (this remains a separate data management task).
- Supporting IaC tools other than Terraform in this initial phase.

## Decisions

- **Tooling**: Terraform will be used due to its robust support for Google Cloud and widespread industry adoption.
- **Modularity**: The Terraform code will be structured into reusable modules to allow for easy scaling and reuse across different project environments.
- **Dynamic Configuration**: The agent's `config.py` will be updated to fetch resource IDs from environment variables, which will be populated by Terraform outputs or a `.env` file generated by Terraform.
- **GCS & IAM**: The IaC solution will include data sources to identify the project number and resource blocks to grant the Vertex AI RAG Service Agent read access to a specified GCS bucket.

## Risks / Trade-offs

- **[Risk]** Resource Name Collisions → **[Mitigation]** Use unique prefixes or suffixes in resource names, controlled by Terraform variables.
- **[Risk]** Permission Issues → **[Mitigation]** Define clear IAM roles and service account requirements in the IaC documentation.
- **[Trade-off]** Initial complexity → **[Rationale]** The upfront effort to set up IaC is justified by the long-term benefits of reproducibility and maintainability.
